# 챗봇 상담 단계·안내 설계

챗봇의 진행률(`progress`)은 **"안내가 얼마나 진행됐는가"**이지 피해가 해결된 정도가 아니다.
무엇이 "완료"인지는 LLM이 아니라 서버 규칙이 정한다.

## 단계와 완료 규칙

| 단계 | 이미지 피해 | 일반 상담 | 완료 조건 (서버가 결정) |
|---|---|---|---|
| SITUATION_CHECK 상황 파악 | O | O | 사용자 메시지가 이미지 피해는 2개, 일반은 3개 이상 |
| EMOTIONAL_SUPPORT 정서 안정 | O | O | 서버가 확인 질문을 건넨 **뒤** 위기 신호 없는 사용자 메시지가 한 번 더 온 경우. 위기 직후에도 같은 방식. 새 위기가 감지되면 다시 진행 중으로 돌아간다 |
| EVIDENCE_PRESERVATION 증거 보존 | O | - | 사용자가 URL을 남겼거나, 서버가 증거 보존 안내를 내보낸 경우 |
| PLATFORM_REPORT 플랫폼 신고 | O | - | 신고 문서가 확정됐거나, 서버가 신고 안내를 내보낸 경우 (신고 문서 작성 시작은 진행 중) |
| AGENCY_GUIDANCE 기관 안내 | O | O | 서버가 기관 안내를 내보낸 경우. 일반 상담은 위기 상담전화를 안내한 경우도 인정 (이미지 피해는 인정하지 않음) |

- LLM 단계 분석(`LlmStageAnalyzer`)은 단계를 **진행 중**으로 표시하는 데까지만 반영된다. 완료로 만들 수 없다.
- 첫 메시지에는 원칙적으로 안내 블록을 붙이지 않는다(먼저 들어주고 상황을 묻는다). 그래서 일반 상담은 첫 메시지 직후 진행률이 0%다. 다만 첫 메시지에서 이미지 피해가 드러났고 증거 URL이 아직 없으면 증거 보존 안내만 바로 붙인다(게시물이 삭제·확산되기 전에 남겨야 해서 시간이 중요하다). 이 경우 첫 응답의 진행률은 20%다.
- 한 턴에 안내 블록은 하나만 붙는다. 순서는 이미지 피해 `증거 → 기관 → 신고 → 정서 확인`, 일반 상담 `정서 확인 → 기관`.
- 일반 상담에서 기관 안내를 마친 뒤 이미지 피해로 바뀌면 기관 안내 단계만 다시 시작한다(디성센터·방심위·경찰은 아직 안내하지 않았으므로). 진행률이 줄어들 수 있다.
- 위기 메시지에는 안내 블록도 종료 제안도 붙지 않는다(고정 위기 응답과 기관 목록만).
- 종료 제안은 **모든 단계가 끝난 바로 그 턴에 한 번만**, 안내 블록 뒤에 덧붙는다. "더 얘기하고 싶어요"라고 답하면 다시 묻지 않는다.
- `/summary`의 `recommendedSteps`는 요청 언어로 번역된 표시용 문구다. 값으로 분기하지 말고 같은 순서의 `recommendedStepCodes`(단계 코드)를 쓴다.
- 응답의 `progress`에는 기존 `progressPercent`에 더해 `completedCount`, `totalCount`(N/M 단계)가 있다. 프론트는 둘 중 편한 쪽을 쓰면 된다.
- 진행 상태는 기존 `stageSnapshot` JSON 컬럼에 저장되므로 DB 마이그레이션은 필요 없다.

코드: `domain/chat/progress/StageRules`(완료 규칙), `domain/chat/guidance/GuidancePlanner`(이번 턴에 붙일 블록),
`GuidanceText`(4개 국어 고정 문구), `AgencyCatalog`(기관 목록), `SafetySignals`(위기·이미지 피해 키워드).
모두 스프링 의존이 없는 순수 로직이다.

## 위기·이미지 피해 감지

`SafetySignals`가 한국어·영어·일본어·중국어(간체) 키워드를 **요청 언어와 상관없이** 모두 검사한다.
위기 키워드는 넓게 잡고, 이미지 피해 키워드는 딥페이크·몸캠처럼 분명한 표현만 단독으로 인정한다.
`유포`, `合成`, `blackmail`처럼 일상에서도 쓰는 표현은 사진·영상·얼굴 같은 이미지 단어와 함께일 때만 이미지 피해로 분류한다.
키워드 사전은 감지의 하한선이지 의료적 판단이 아니다. 놓치는 문장이 있을 수 있으므로 `scripts/chat-eval`에
실제 사례를 계속 추가한다. 위기 쪽은 오탐보다 미탐이 더 위험하다고 보고 넓게 잡았다(예: "포기하고 싶"은 일상 표현에도 걸린다).

## LLM 답변의 번호 환각 방지

프롬프트로 기관 이름·전화번호를 말하지 못하게 하고, 서버가 `ReplyGuard`로 한 번 더 막는다. LLM 답변에 `AgencyCatalog`에 없는 3자리 이상 번호가
있으면(사용자가 쓴 숫자, 연도, 퍼센트는 제외) 그 답변을 버리고 룰 기반 고정 답변을 보낸다. 오탐이면 LLM 답변이 고정 답변으로 바뀔 뿐이라 안전한 쪽으로 실패한다.
`scripts/chat-eval` 러너도 같은 기준으로 답변의 번호를 검사하므로, LLM을 켠 서버에서 돌리면 실제 환각을 잡아낸다.

### `data.sql`과 챗봇의 불일치 (팀 결정 필요)

`src/main/resources/data.sql`의 `agencies` 시드(기관 조회 API가 사용)에는 챗봇이 더 이상 쓰지 않는 번호가 남아 있다.

- `1393` 한국생명존중희망재단 자살예방상담전화 → 109로 통합됨
- `1577-0199` 정신건강 위기상담전화 → 통합 후 유지 여부를 확인하지 못함
- `182` 경찰청 사이버수사국 → 챗봇은 112 / ecrm.police.go.kr만 안내. 182의 용도(경찰 민원 콜센터)를 확인하지 못함

챗봇만 먼저 고쳐서 두 곳이 서로 다른 번호를 보여 줄 수 있다. `AgencyDataSqlIntegrationTest`가 시드를 검증하므로
`data.sql`을 바꿀 때는 그 테스트도 함께 수정해야 해서 이번 변경에서는 건드리지 않았다.

## 평가

`scripts/chat-eval/`에 25개 시나리오와 러너가 있다. 서버를 띄운 뒤 실행한다.

```bash
CHAT_LLM_ENABLED=false ./gradlew bootRun         # LLM 없이 결정론적으로 재현
python3 scripts/chat-eval/run_eval.py --base-url http://localhost:8080
python3 scripts/chat-eval/run_eval.py --only crisis --report /tmp/chat-eval.json
```

채점하는 것은 서버가 코드로 보장해야 하는 항목이다: 위기 감지와 기관 안내, 기관 목록에 없는 번호가 답변에 나오지 않는지,
단계가 언제 완료되는지, 종료 제안 횟수, 한 턴에 완료되는 단계 수, 요청 언어에 다른 언어(한글)가 섞이지 않는지.
LLM이 쓴 문장의 품질(공감, 자연스러움)은 채점하지 않는다. 그 부분은 사람이 대화 로그를 읽고 평가해야 한다.
시나리오마다 새 `X-Anonymous-Id`를 쓰므로 운영 서버가 아니라 로컬·개발 서버에서만 돌린다.
